# StackChan 实时语音交互设计

日期：2026-10-26。状态：需求与设计草案，尚未实现。整机阶段见 [总体规划](ROADMAP.md)。

用户已明确要求实时监听、可以打断、说话结束自动发送。正常交互不依赖点击录音按钮；设备播报期间仍要听到用户说话。本文规定本地声音处理、自动断句、交互替换和验收方式，具体阈值在实机上调整。

## 监听与上传

设备在线、服务就绪且监听开关开启时，麦克风持续采集，音频前端持续处理。无论当前在等待、思考、调用工具还是播放回复，都要保留检测新语音的能力。用户关闭麦克风、主动暂停监听或进入维护模式时停止对话采集并清理临时音频缓存。

空闲声音只进入有上限的本地环形缓冲。检测到有效语音后，创建新的 utterance/interaction 标识，携带开头预留音频开始 Opus 流式上传；检测到说话结束后发送一次结束标记，自动提交该轮处理。这样“结束自动发送”表现为自动提交已经上传的语音流，不需要先录完整段再上传。

不发声时不产生空轮次；句中短暂停顿不提交；达到最大句长时以明确的限制原因结束当前输入，不静默丢弃尾部。网络断开则中止本轮并说明失败，不缓存无限长的录音等待重连，也不自动重放旧任务。

## 本地声音处理链路

```mermaid
flowchart LR
    Mic[麦克风持续采集] --> Align[采样率与时序对齐]
    Ref[实际播放的 PCM 参考] --> Align
    Align --> AFE[AEC 与降噪]
    AFE --> VAD[VAD 与自动断句]
    VAD --> Buffer[有界预留缓冲与语音帧]
    Buffer --> Opus[Opus 编码与流式上传]
    VAD --> Interrupt[本地语音打断]
    Interrupt --> Stop[停止旧播放和交互关联动作]
```

先验证硬件能同时录音和播放，再把实际送往扬声器的 PCM 作为 AEC 参考，处理重采样、音量、时序与输出延迟。不能拿原始 TTS 文本或未经设备处理的压缩数据直接作参考。下行播放若采用 24 kHz、前端采用 16 kHz，需要对参考和采集作一致的采样率与时序处理，并在插话停止播放时正确处理残余回声。

Espressif ESP-SR AFE 提供 AEC、降噪和实时 VAD，并区分麦克风与播放参考通道，可作为候选实现。其接口包含前端帧长、通道排列和 VAD 缓存要求；实现须依据最终锁定版本处理缓存和前端延迟，不能假设 Opus 20 ms 帧长等于 AFE 输入帧长。[官方 AFE 说明](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/audio_front_end/README.html)

AFE 组件、模型分区和内存预算尚未引入当前工程。先测 ESP32-S3 上同时运行采集、AEC/VAD、Opus、播放、Wi-Fi 与 UI 的资源占用，再冻结组件版本和参数。麦克风持续开启和声音可同时采集/播放是基础条件，可靠识别人声插话还要通过双讲和自激测试。

## 自动断句参数候选

| 参数 | 初始候选 | 作用 |
| --- | --- | --- |
| 输入 | 16 kHz、PCM16，前端输出单声道 | 原始麦克风通道数量以板级验证为准 |
| Opus | 20 kbps、20 ms | 与总体规划一致，前端输出按需重分帧 |
| 开头预留 | 约 300 ms | 补回 VAD 检测前的音节；与前端自带缓存合并去重 |
| 开始确认 | 约 80–160 ms 的持续有效语音 | 抑制瞬时噪声，仍需测量检测延迟 |
| 结束静音 | 约 600–900 ms | 自动结束本轮，兼顾句中停顿与响应速度 |
| 最短有效语音 | 约 150–250 ms | 过滤杂音，需要保留“好”“停”等短指令 |
| 单句上限 | 先评估 30 秒 | 防止异常长录音耗尽资源，超限原因可见 |

这些是调参起点，不是已完成的性能指标。VAD 后处理、环形缓存和编码缓存应共享明确的时间基准，避免重复上传或吞掉第一个字。静音末尾可以保留必要尾音，但不能因多个任务各自超时而重复提交。

## 播报中打断

正常模式无需先说唤醒词。AEC 后的近端有效人声满足开始条件时，触发本地打断；不等待 STT 返回文字，不等待 Agent 决定停不停，也不靠单一音量阈值判断。

1. 立即停止旧播放源、解码输出和硬件播放缓冲，禁止迟到的旧音频重新启动。
2. 使旧交互失效，清理旧轮次的待播字幕、动画实例、临时默认映射和动作；恢复当前真实状态的默认表现，本地关联动作立即停止。
3. 保留新语音的预留与当前音频，建立新输入流；声音采集不因停止旧播放而丢失。
4. 向 Studio 发送带旧交互标识的中断，同时提交新轮次标识；旧轮次的取消确认与新语音上传可以并行。
5. Studio 取消旧 Agent/语音队列，阻止旧 Agent 继续发出设备命令；不可取消的已完成外部操作保持真实结果。

执行播放停止和开启新流时仍保持 AEC 参考链路时序正确，避免停止瞬间的残余回声被误认成第二次插话。单次插话只生成一次交互替换事件。

思考、工具运行或提交上一轮后又开始说话，同样按新交互替换处理。首版不隐式把两轮合并成一段，也不同时启动多个争用设备的 Agent。后续如需“补充上一句话”应另定明确的合并窗口。

## 状态与交互归属

| 状态维度 | 规划值与转换 |
| --- | --- |
| 监听 | 开启 / 用户关闭 / 主动暂停 / 故障；与思考和播放并行 |
| 输入分段 | 等待人声 → 语音中 → 等待句尾 → 已提交；恢复说话则继续本句 |
| 回复 | 无回复 / 思考 / 工具运行 / 播放 / 已结束；任何阶段可被新语音替换 |
| 关联 | utteranceId、interactionId、当前交互代次；以最终协议命名为准 |
| 中断 | 旧交互进入终止状态；新一轮拥有不同标识，旧回调不得更新新一轮 |

DeviceControl 和 Studio MCP 桥接都要校验设备、连接会话与交互代次。新语音打断后，旧 Agent 即使尚未完全停止，也不能再通过工具把旧动作加入队列。音频播放确认区分完成与中断，不能把清空队列报告成正常播完。

触屏提供监听开关与停止入口。关闭监听后不再自动开始新语音轮次；重新开启前清理旧缓冲。屏幕待机保留已经开启的监听，主动暂停监听的睡眠模式停止对话采集，详见总体规划。

## Studio 与 MCP 的职责

连续音频仍通过设备音频通道上传，由 Studio 完成 STT、目标 Agent 路由与 TTS。Studio 为每轮提供同一套交互身份，后续把该轮分配给用户配置的专用 Agent。

MCP 提供动作、动画、设备查询和设置等工具，复用设备控制服务；不把音频或动画逐帧包装成 Agent 工具调用。停止旧语音、自动断句与新流建立是实时控制逻辑，不等待 MCP 调用完成。具体方法见 [设备控制设计](DEVICE-CONTROL.md) 与 [动画控制设计](ANIMATION-CONTROL.md)。

## 验收门槛

| 场景 | 通过标准 |
| --- | --- |
| 自动对话 | 连续至少 10 轮，无需点击开始或结束，句尾自动提交且每轮只提交一次 |
| 句首与句尾 | 轻声、短指令、句中停顿和长句测试中不丢首字、不随短暂停顿拆句；超限可解释 |
| 双讲打断 | 不同播放音量下用户开口可打断，并保存新一句开头；旧声音、字幕和动作不再回流 |
| 回声与噪声 | 仅播放设备自身声音不触发新轮；风扇、敲击、音乐等场景记录误触发，不用静音麦克风掩盖问题 |
| 停止时延 | 本地确认新语音后到停止旧声音目标 ≤200 ms；从用户开口算的总目标 ≤400 ms，分别实测并报告分位值 |
| 自动提交时延 | 从末尾有效人声到提交目标约 600–1000 ms，包含前端与断句延迟；与服务器回复延迟分开记录 |
| 连续打断 | 至少 10 次连续插话，播放缓冲、交互代次和 Agent 动作始终一致，无旧轮次复活 |
| 启停与断线 | 静音/主动暂停时无上传；恢复无旧音频；断线中止本轮，恢复不重发旧任务 |
| 资源 | 持续录放音、UI 和网络并行，记录 CPU、内部内存/PSRAM、水位和欠载；不靠停监听规避压力 |

唤醒词是后续可选入口，AEC/VAD、自动断句与语音打断是首版实时对话必需能力。手动半双工测试可用于板级排障，不能替代上述验收。
